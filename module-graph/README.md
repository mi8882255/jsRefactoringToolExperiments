# module-graph

Строит граф зависимостей между модулями проекта на основе AST (через
`@babel/parser` + `@babel/traverse`) и рисует его как интерактивный граф.

Поддерживаются:

- CommonJS: `require('x')`, `require.resolve('x')`, `import x = require('y')` (TS)
- ES-модули: `import`, `import type`, `export { x } from 'y'`, `export * from 'y'`, `export type { x } from 'y'`
- Динамический импорт: `import('x')`
- `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx` (TypeScript и JSX парсятся из коробки, без `tsc`)

Относительные импорты резолвятся в реальные файлы на диске (с учётом
расширений и `index.*`). Импорты пакетов (`react`, `lodash`, ...) помечаются
как внешние, встроенные модули Node (`fs`, `path`, ...) полностью исключаются
из графа — это просто шум. Нерезолвящиеся относительные импорты и файлы с
ошибками парсинга отдельно подсвечиваются на графе. Инструмент также находит
циклические зависимости между модулями.

Дополнительные фичи:

- **Прогрессивное раскрытие графа** — по умолчанию видны только entry-point'ы
  (файлы, которые никто не импортирует), свёрнутые. На свёрнутом узле бейдж
  `▸N·dD` показывает, сколько файлов и на какую глубину скрыто внутри него.
  Клик по узлу → в сайдбаре кнопка "Show dependencies" разворачивает его прямых
  зависимостей на один уровень; кнопка "Show who imports this" (`◂N·dD`) идёт
  **в обратную сторону** — например, кликнуть на клиент БД и посмотреть, кто
  его использует, даже через несколько уровней импортов. Это решает проблему
  "слишком много узлов сразу" на больших проектах — граф строится по шагам,
  а не весь целиком.
- **Layout** — иерархический, слева-направо (entry points слева, дальше вглубь
  зависимостей вправо), без физики/симуляции — узлы не "дрожат" и не ездят.
  Изолированные файлы (нет ни импортов, ни импортёров) не рисуются на холсте
  вообще — они просто текстом в сайдбаре ("N isolated files"), чтобы не мешать.
  Есть чекбокс "Show everything", чтобы одним кликом вернуться к старому виду
  (весь граф целиком, без раскрытия по шагам) — для небольших проектов это
  может быть удобнее.
- **Diff-режим (`--diff`)** — помечает файлы, изменённые по git diff, и всё,
  что их транзитивно импортирует ("blast radius" изменения). Полезно перед
  код-ревью: сразу видно, что реально затронуто, а не только что изменено
  построчно.
- **Мульти-проектный режим (включён по умолчанию)** — если в сканируемой
  папке лежит несколько проектов (несколько `package.json`), инструмент
  распознаёт импорт одного проекта по имени пакета другого (`require('shared-utils')`)
  как связь между проектами, а не как обычную внешнюю зависимость, и
  добавляет отдельный "Project graph" — агрегированный граф связей между
  самими проектами (без шума от node_modules/стандартных библиотек).
- **Interfaces/DI-граф** — отдельный режим "Interfaces", который находит
  TS `interface`/`abstract class` и классы, которые их `implements`/`extends`
  (включая объявление и реализацию в разных файлах — как раз паттерн, когда
  интерфейс описан в одном месте, а конкретная реализация подставляется через
  DI где-то ещё). Обычное `class B extends A` для не-abstract `A` сюда не
  попадает — только то, что реально похоже на интерфейс/реализацию.
- **CSV-экспорт** — тот же граф в виде плоской таблицы: `--csv` (список связей
  from→to) и `--csv-nodes` (один файл = одна строка, с метаданными: роль,
  глубина, diff-флаги).

## Запуск

```bash
npm install            # один раз, из корня репозитория

# сгенерировать самостоятельный HTML-отчёт
node module-graph/cli.js ./src --out report.html
# или
npm run graph -- ./src --out report.html

# поднять локальный сервер с кнопкой "Rescan" (пересканирует проект заново)
node module-graph/cli.js ./src --serve --port 4321

# подсветить, что затронуто незакоммиченными изменениями
node module-graph/cli.js . --diff --out report.html

# тот же diff, но live: правите код, жмёте "Rescan" — подсветка обновляется
node module-graph/cli.js . --serve --diff

# тот же граф, но как таблица (CSV) - связи + метаданные по файлам
node module-graph/cli.js . --csv edges.csv --csv-nodes nodes.csv
```

Опции:

| Флаг             | Описание                                                        |
| ---------------- | ---------------------------------------------------------------- |
| `target-dir`     | Какую директорию сканировать (по умолчанию — текущая)            |
| `--out <file>`   | Куда писать standalone HTML-отчёт (по умолчанию `module-graph-<папка>-<случайный>.html`, чтобы не затирать предыдущие прогоны) |
| `--json <file>`  | Дополнительно сохранить сырые данные графа как JSON               |
| `--csv <file>`   | Дополнительно сохранить граф как таблицу связей (`from,to,kind,...`) |
| `--csv-nodes <file>` | Дополнительно сохранить таблицу файлов (роль, глубина, diff-флаги, ...) |
| `--serve`        | Поднять express-сервер с живым пересканом вместо записи файла     |
| `--port <n>`     | Порт для `--serve` (по умолчанию 4321)                            |
| `--no-external`  | Не включать внешние пакеты (`node_modules`) в граф                |
| `--diff [spec]`  | Подсветить изменённые файлы + всё, что их импортирует. `--diff` без аргумента — незакоммиченные изменения (staged + unstaged + новые файлы); `--diff main` — изменения относительно `main`, включая незакоммиченные; `--diff "main HEAD"` — строго между двумя ref'ами |
| `--no-projects`  | Отключить автоопределение соседних проектов и связи между ними через имя пакета |
| `--extra-builtins a,b` | Дополнительно считать "стандартной библиотекой" (и исключать из графа) указанные через запятую имена, сверх встроенных модулей Node |
| `--show-builtins` | Не исключать встроенные модули Node вообще — показывать их как обычные внешние узлы |

### Как поменять список "стандартных библиотек"

По умолчанию из графа полностью убираются модули из `require('module').builtinModules` —
то есть актуальный список самого Node.js (`fs`, `path`, `http`, ...), в т.ч. с префиксом `node:`.
Три способа подстроить это под себя:

1. **Добавить что-то своё в исключения** — например, внутренний полифил или шим,
   который есть в любом проекте и не несёт архитектурного сигнала:
   ```bash
   node module-graph/cli.js . --extra-builtins "my-internal-polyfill,@company/bootstrap"
   ```
2. **Вообще отключить исключение** — если хочется увидеть, кто и сколько использует
   `fs`/`path`/etc:
   ```bash
   node module-graph/cli.js . --show-builtins
   ```
3. **Поменять сам список навсегда** — отредактировать `module-graph/src/resolveModule.js`:
   `BUILTIN_SET` там строится из `require('module').builtinModules`; если нужно
   зашить туда что-то постоянно (а не каждый раз флагом), добавьте это прямо в
   `BUILTIN_SET` при инициализации, например:
   ```js
   const BUILTIN_SET = new Set([...builtinModules, "my-internal-polyfill"]);
   ```

По умолчанию игнорируются `node_modules`, `.git`, `dist`, `build`, `out`,
`coverage`, `.next`, `.cache`, `legacy` и любые dot-директории.

## В отчёте

- **По умолчанию видны только entry points.** Клик по узлу открывает в сайдбаре
  карточку с кнопками "Show dependencies (N files, depth D)" и "Show who imports
  this (N files, depth D)" — каждая раскрывает соответствующих соседей на один
  шаг. Повторный клик по кнопке — свернуть обратно. Бейдж `▸N·dD`/`◂N·dD` прямо
  на узле показывает то же самое без клика.
- **Даблклик по узлу** — быстрый способ раскрыть/свернуть без похода в сайдбар:
  по умолчанию раскрывает зависимости (вниз), если их нет — раскрывает импортёров
  (вверх). Повторный даблклик сворачивает обратно.
- При раскрытии/сворачивании **камера не двигается и ничего на экране не
  переезжает** — новые узлы дорисовываются рядом с тем, который вы раскрыли
  (как ветка дерева), а не пересчитывают весь layout заново. Если открытое
  оказалось за пределами видимой области — просто подвиньте холст (drag) или
  зумните колесом, как в любой карте.
- При клике/даблклике по узлу **подсвечивается именно его поддерево** (всё,
  что с ним связано среди уже показанного, в обе стороны) — остальное гаснет
  (opacity вниз), чтобы не путать с другими ветками, раскрытыми раньше.
- Чекбокс "Show everything" — отключить раскрытие по шагам и показать весь граф сразу. Раскладка
  послойная: слева то, что никто не импортирует, дальше по глубине импортов вправо; внутри слоя
  узлы упорядочены по положению родителей (меньше пересечений), высокие слои переносятся в
  несколько колонок. Циклы этой раскладке не мешают.
- **Строки статистики кликабельны** — клик показывает на графе именно то, о чём строка:
  внешние пакеты (+ файлы, которые их используют), изолированные файлы, все циклы или
  конкретный цикл из списка "Cycles" (рисуются кольцами, рёбра цикла красные; циклы с
  общими файлами сливаются в одно кольцо), файлы с ошибками парсинга, изменённые/затронутые
  по diff. "files"/"edges" включают "Show everything", "interface links"/"sub-projects"
  переключают на соответствующий режим. Сверху сайдбара появляется плашка "Focused on …"
  с кнопкой "Clear focus".
- Кнопка "Reset to entry points" — свернуть всё обратно к началу.
- Список изолированных файлов (ни импортов, ни импортёров) — отдельно под чекбоксами, не на холсте.
- Поиск по пути файла (фильтрует среди уже показанных узлов).
- Переключатель "Show external packages".
- Если найден diff — чекбокс "Show only changed/impacted", чтобы видеть только затронутый подграф.
- Если найдено больше одного проекта — кнопка "Project graph" (агрегированный граф связей между проектами).
- Если найдены interface/implements-связи — кнопка "Interfaces" (отдельная UML-подобная диаграмма: класс → реализуемый интерфейс).
- Панель статистики: количество файлов, связей, внешних пакетов, изолированных файлов, исключённых builtin-импортов, найденные циклы, ошибки парсинга, число изменённых/затронутых файлов по diff, число interface-связей.
- Цвет узла: зелёный — входная точка, синий — обычный модуль, серый — внешний пакет, фиолетовый — интерфейс соседнего проекта (имя пакета совпало, но точный файл не найден), красный — импорт, который не резолвится в файл, оранжевый — файл с ошибкой парсинга.
- Толстая цветная рамка узла в diff-режиме: красная — файл изменён, жёлтая — файл импортирует что-то изменённое (затронут транзитивно).
- Фиолетовое ребро — связь, пересекающая границу проекта (через имя пакета или через relative-импорт, который физически залез в папку другого проекта).
- В Interfaces-режиме: ромб — интерфейс/abstract class, кружок — реализующий класс, подписанная стрелка — `implements`/`extends`.

Для отладки/автоматизации страница кладёт текущий граф и вызов сети в
`window.__moduleGraph` (`graph`, `state`, `getNetwork()`) — доступно прямо
в devtools-консоли браузера.

## Структура

```
module-graph/
  cli.js                точка входа
  src/
    scan.js             обход директории
    parseFile.js        Babel-парсер (JS/JSX/TS/TSX)
    extractImports.js   обход AST, сбор всех вариантов импорта
    extractInterfaces.js обход AST, сбор interface/implements/extends
    resolveModule.js    резолв специфаеров в абсолютные пути + builtin/cross-project
    projects.js         автоопределение соседних проектов (package.json) по имени пакета
    gitDiff.js          git diff -> список изменённых файлов
    exportCsv.js         граф -> CSV (edges / nodes)
    buildGraph.js        сборка графа + метрики глубины/роли + циклы + diff + project graph + interface graph
    renderHtml.js         HTML-шаблон отчёта
    clientApp.js          клиентский JS (vis-network): раскрытие по шагам, 3 режима просмотра
    server.js             express-сервер для --serve
```

## Ограничения

- Динамические специфаеры (`require(someVar)`, `` require(`${x}`) ``) не анализируются — учитываются только строковые литералы.
- Алиасы путей из `tsconfig.json` (`@/utils`, ...) не резолвятся напрямую — если алиас совпадает с именем соседнего проекта, он подхватится через мульти-проектный резолв, иначе попадёт во "внешние".
- Связь между проектами резолвится только по имени пакета (`package.json#name`) и его `main`/`module` полю — условные `exports` (`package.json#exports` с map'ом путей) не разбираются, в таком случае узел помечается как "interface" без точного файла.
- Метрики глубины/количества зависимостей считаются BFS от каждого узла (`O(N·(N+E))`) — для проектов в сотни-тысячи файлов это доли секунды, но на действительно огромных монorepo может быть заметно медленнее; пока не оптимизировано.
- `implements` всегда создаёт связь в Interfaces-графе (даже если объявление интерфейса не найдено — тогда рисуется placeholder-узел), а обычный `class B extends A` считается "интерфейсной" связью только если `A` — `abstract class` или сам объявлен через `interface extends`; иначе это просто обычное наследование, и оно туда не попадает.
